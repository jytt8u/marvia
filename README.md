# Veil

Инфраструктура для обхода сетевой цензуры: собственный протокол, ядро, ноды,
управление и клиенты.

**Текущий этап: M3.** Работает шифрованный туннель с взаимной
аутентификацией, замаскированный под обычный HTTPS: клиент здоровается с
отпечатком Chrome, размеры пакетов размыты добивкой, десятки соединений
пользователя идут через одно соединение до ноды, а тот, кто пришёл без
правильного ключа, получает настоящий сайт вместо разрыва. Нода ведёт учёт
трафика по пользователям, следит за квотами, сроками подписки и числом
устройств.

- как всё устроено целиком — [docs/architecture.md](docs/architecture.md)
- протокол и то, что видно снаружи — [docs/protocol.md](docs/protocol.md)

## Сборка

Нужен Go 1.24+.

```bash
go build -o bin/ ./...
```

Четыре бинарника: `veil-keygen`, `veil-server`, `veil-client`, `veil-panel`.

Для Linux-ноды из-под Windows:

```bash
GOOS=linux GOARCH=amd64 go build -o bin/linux/ ./...
```

## Быстрый старт

**1. Ключи**

```bash
./bin/veil-keygen
```

Приватный остаётся на ноде, публичный нужен клиенту.

**2. Нода**

```bash
VEIL_SERVER_KEY=<приватный ключ> ./bin/veil-server -listen :443 -tls-cert fullchain.pem -tls-key privkey.pem -cover https://example.org
```

Ключ передавай переменной окружения или `-key-file`: значение флага `-key`
видно в `ps` любому пользователю машины.

`-cover` — адрес настоящего сайта, который увидит всякий, кто зайдёт на домен
ноды браузером или сканером. **Это не украшение, а защита**: нода, молча
рвущая непонятные соединения, вычисляется активным зондированием за пару дней.

### Маскировка REALITY

Вместо собственного сертификата нода может прикрываться чужим настоящим
сайтом. Тогда свой домен и сертификат не нужны вовсе.

```bash
./bin/veil-keygen -reality
```

```bash
VEIL_REALITY_KEY=<приватный ключ> ./bin/veil-server -listen :443 \
  -reality-dest www.samsung.com:443 -reality-sni www.samsung.com \
  -panel https://panel.example.com -panel-token <токен ноды>
```

Как это работает: на каждое входящее соединение нода открывает своё к сайту
прикрытия и зеркалит туда ClientHello. Тот, кто не доказал право входа,
получает **настоящий чужой сайт** — его содержимое и его подлинный
сертификат. Отличить ноду от зеркала того сайта нельзя, потому что в этот
момент она им и является.

Проверено вживую: `curl` с полной проверкой сертификата (`ssl_verify_result 0`)
подключился к ноде, прикрытой `www.example.com`, и получил страницу, побайтно
совпадающую с настоящей.

Чем это лучше обычного TLS с нашим сертификатом:

| | Свой сертификат | REALITY |
|---|---|---|
| Отпечаток ответа | стандартный Go, отличается от nginx | берётся у настоящего сайта |
| Свой домен | нужен, блокируется по SNI | не нужен вовсе |
| Что видит сканер | наш сайт-заглушку | чужой популярный сайт с валидным замком |
| Продление сертификата | нужно | не нужно |

**Как выбирать сайт прикрытия.** Он должен поддерживать TLS 1.3 и HTTP/2, быть
популярным, не принадлежать тебе и не лежать в подсети ноды. Плохой выбор
выдаёт ноду: сайт, к которому из этой страны никто не ходит, сам по себе
аномалия.

`-reality-short-id` — короткие идентификаторы клиентов через запятую,
шестнадцатеричные. Позволяют отзывать группы клиентов, не меняя ключ ноды.

Публичный ключ REALITY нода печатает при запуске — его нужно вписать в панель
как `pbk`, чтобы в ссылки уходило `security=reality`.

### Работа за CDN: адрес ноды не существует

REALITY прячет трафик, но не адрес. Под ковровую блокировку диапазонов
хостингов — как 4 августа 2026 года — попадает и безупречно замаскированная
нода, потому что её никто не разглядывал.

Ответ на это один: **не показывать адрес вовсе**. Пользователь подключается к
адресам CDN, за которыми живут миллионы обычных сайтов; заблокировать такой
диапазон целиком означает уронить пол-интернета.

```bash
./bin/veil-server -listen :443 -ws-path /assets/app.js \
  -tls-cert fullchain.pem -tls-key privkey.pem -cover https://example.org
```

Домен направляешь на CDN, CDN — на ноду. В конфиге покупателя стоит домен, а
не адрес сервера.

```bash
./bin/veil-client -server <адрес CDN>:443 -ws-host <домен> -ws-path /assets/app.js -pubkey <ключ>
```

Проверено вживую: 11 запросов пользователя прошли через одно соединение до
ноды — мультиплексирование работает и внутри WebSocket.

**Путь стоит делать неочевидным.** Перебор популярных вроде `/ws` или `/vless`
по всем адресам хостера — дешёвый способ искать ноды. При этом сам по себе
путь туннеля ничем не выделяется: запрос без переговоров о WebSocket получает
ровно то же, что и любой другой путь.

| Путь | Что отдаёт нода |
|---|---|
| `/` | сайт-прикрытие, 200 |
| `/ws`, `/vless`, `/api` | сайт-прикрытие, 404 |
| путь туннеля обычным запросом | сайт-прикрытие, 404 |
| путь туннеля с переговорами | туннель |

**CDN видит расшифрованный трафик** — он же терминирует TLS. Здесь окупается
слоёная архитектура: внутри WebSocket работает VP1 со своим шифрованием, и CDN
достаётся поток, который он прочитать не может.

**REALITY и CDN несовместимы.** REALITY требует прямого TCP до ноды, а CDN
расшифровывает TLS у себя. Это два ответа на две разные угрозы:

| Режим | Что прячет | Чем платим |
|---|---|---|
| REALITY на чистом адресе | трафик неотличим от чужого сайта | адрес виден, попадает под ковровые блокировки |
| WebSocket за CDN | адреса для цензора не существует | камуфляж слабее, CDN видит зашифрованный нами поток |

Продавец выбирает под конкретную ноду; панель собирает ссылки под оба режима.

**3. Клиент**

```bash
./bin/veil-client -server <домен>:443 -sni <домен> -pubkey <публичный ключ>
```

**4. Проверка**

```bash
curl -x socks5h://127.0.0.1:1080 https://api.ipify.org
```

Должен вернуться IP ноды. Схема именно `socks5h`: `h` означает, что домен
резолвит нода, иначе DNS-запросы уйдут мимо туннеля и выдадут всё, что ты
открываешь.

Проверить прикрытие — должен открыться сайт из `-cover`:

```bash
curl https://<домен>/
```

### Локальная проверка целиком

На Windows из PowerShell:

```powershell
.\scripts\smoke.ps1
```

На Linux, macOS и в Git Bash:

```bash
bash scripts/smoke.sh
```

Поднимает ноду и клиента на localhost с самоподписанным сертификатом и
проверяет три вещи: трафик через туннель ходит, мультиплексирование работает,
посторонний видит сайт-прикрытие.

### Отладка вручную

```bash
./bin/veil-server -key <приватный> -tls-self-signed cover.local -cover https://example.com
./bin/veil-client -server 127.0.0.1:8443 -sni cover.local -insecure -pubkey <публичный>
```

Флаг `-plain` с обеих сторон отключает маскировку целиком — удобно, когда
отлаживаешь сам протокол и не хочешь мешать слои.

## Клиент для Android

Ядро готово и кросс-компилируется под `android/arm64`. Приложения ещё нет —
и вот что для него нужно.

### Что уже работает

```
mobile/              библиотека для gomobile bind: Start, Stop, NodeName
internal/client      разбор ссылки доступа, список нод, дозвон до цели
internal/tunbridge   пакеты сетевого интерфейса → потоки туннеля
```

Разделение такое: приложение на Kotlin поднимает `VpnService`, получает от
системы дескриптор интерфейса и отдаёт его в Go. Дальше всё делает Go. Тот же
код работает на настольной машине под SOCKS — логика не дублируется между
платформами, иначе каждую ошибку пришлось бы чинить трижды.

**Свой стек TCP мы не пишем.** Android даёт сырые IP-пакеты, а туннелю нужны
соединения — кто-то должен выполнить работу сетевого стека. Берём проверенный
gvisor через `tun2socks` по той же причине, по которой не писали свой TLS.

**Запросы имён уходят в туннель по TCP.** Наш протокол UDP пока не проксирует,
а запрос имени, ушедший мимо туннеля, выдаёт цензору весь список посещённых
сайтов, даже когда трафик он расшифровать не может. Перевод UDP → TCP — часть
стандарта, а не обходной манёвр.

### Что нужно установить

Ничего из этого на машине сейчас нет — есть только JDK 21.

| Что | Зачем | Размер |
|---|---|---|
| Android SDK (command-line tools) | сборка APK | ~600 МБ |
| Android NDK | `gomobile bind` без него не работает | ~2,5 ГБ |
| `gomobile` | сборка Go в AAR | несколько МБ |

```bash
go install golang.org/x/mobile/cmd/gomobile@latest
gomobile init
gomobile bind -target=android/arm64,android/arm -o veil.aar ./mobile
```

### Чего ещё нет

- приложения на Kotlin: `VpnService`, экран подключения, импорт ссылки;
- выбора ноды по замерам с самого устройства — сейчас берётся первая
  подходящая. Панель стоит за границей и видит ноду живой тогда, когда для
  телефона в Иркутске она уже мертва;
- клиента REALITY: к таким нодам приложение подключиться не сможет и честно
  об этом скажет, а не будет молча выглядеть как «интернет не работает».

## Отчёты о доступности и выбор ноды

Панель стоит за границей и видит ноду живой ровно тогда, когда для телефона в
Иркутске она уже мертва. Единственный, кто знает правду, — само устройство.

**Клиент меряет ноды сам** и подключается к самой быстрой живой. Меряется не
время установки TCP, а время до работающего туннеля: заблокированная нода
обычно принимает соединение и молча роняет пакеты уже во время TLS, так что
проверка «порт открыт» показала бы её живой.

**Результаты уходят панели** на `POST /sub/{token}/report` — тем же токеном
подписки. Админского токена на устройстве покупателя быть не должно ни при
каких обстоятельствах.

Панель складывает отчёты и ставит ноды в подписке в том порядке, в каком их
стоит пробовать. В интерфейсе у каждой ноды видно «сколько людей доходят» и
медианную задержку — продавец узнаёт о блокировке из панели, а не из
обращений в поддержку.

### Почему отчёты не отключают ноды

Отчёты приходят от клиентов, то есть из недоверенного источника. Если бы
жалоба была командой, любой покупатель выкинул бы все ноды продавца из
подписок и убил сервис без всякой блокировки.

Поэтому три правила:

| Правило | Что оно предотвращает |
|---|---|
| от каждого подписчика хранится один последний отчёт на ноду | накрутку количеством сообщений |
| ноды не отключаются, а только переставляются в списке | уничтожение сервиса одним вредителем |
| проблемной нода считается от трёх разных жалобщиков | ложные срабатывания от одного человека с плохой связью |

Худшее, чего добьётся вредитель, — подвинет живую ноду вниз списка.

## Пользователи, квоты и учёт

По умолчанию нода пускает любого, кто знает её публичный ключ. Для реальной
работы нужен файл пользователей — он же список того, кто и сколько может.

**Простой формат** — когда пользователей трое и лимиты не нужны:

```
# ноутбук
ЗДЕСЬ-ПУБЛИЧНЫЙ-КЛЮЧ-КЛИЕНТА-43-СИМВОЛА
```

**Полный формат** — с подписками и лимитами:

```json
{
  "users": [
    {
      "kind": "vp1",
      "secret": "ЗДЕСЬ-ПУБЛИЧНЫЙ-КЛЮЧ-КЛИЕНТА-43-СИМВОЛА",
      "label": "заказ 1043",
      "enabled": true,
      "expires_at": "2026-09-23T00:00:00Z",
      "traffic_limit": 107374182400,
      "max_ips": 3,
      "max_conns": 8,
      "account": "1043"
    },
    {
      "kind": "vless",
      "secret": "94183e3f-c094-4c62-9c8a-431fea85aa04",
      "label": "телефон",
      "enabled": true,
      "traffic_limit": 107374182400,
      "account": "1043"
    },
    {
      "kind": "trojan",
      "secret": "пароль",
      "label": "ноутбук",
      "enabled": true,
      "traffic_limit": 107374182400,
      "account": "1043"
    }
  ]
}
```

`kind` — вид доступа: `vp1` (умолчание, наш протокол), `vless` или `trojan`.
Последние два нужны, чтобы покупатель пользовался приложением, которое у него
уже стоит: v2rayNG, Hiddify, NekoBox. Нода понимает все три на одном порту и
различает их по первым байтам.

`account` связывает наборы в один аккаунт: квота, срок и лимит адресов у них
общие. Без него каждый набор получил бы свой лимит, и достаточно было бы
попросить второй конфиг, чтобы удвоить себе трафик.

Прежнее поле `public_key` по-прежнему понимается и означает то же, что
`secret` при `kind: vp1`.

```bash
./bin/veil-server -users users.json
```

| Поле | Что делает |
|---|---|
| `enabled` | `false` — доступ приостановлен, статистика сохраняется |
| `expires_at` | конец подписки; пусто — бессрочно |
| `traffic_limit` | байт всего; 0 — без лимита |
| `max_ips` | со скольких разных адресов можно подключаться в течение часа |
| `max_conns` | одновременных соединений до ноды; с мультиплексированием одно устройство открывает до четырёх |

`max_ips` — ответ на главную боль продавца: один купил, раздал конфиг
десятерым. Считать устройства напрямую нельзя, все предъявляют один ключ, а
вот разные адреса видно. Окно в час выбрано, чтобы переход с Wi-Fi на
мобильную сеть не упирался в лимит.

**Файл перечитывается на лету**, каждые 5 секунд по времени изменения:
панель или скрипт бота просто перезаписывают его. Если файл окажется битым,
нода продолжит работать по прошлому списку — отключить всех из-за опечатки
в конфиге хуже, чем на минуту отстать от изменений.

**Расход пишется рядом**, в `users.json.usage.json` (переопределяется флагом
`-usage`), каждые 30 секунд и при остановке. Перезапуск ноды не обнуляет
счётчики — иначе месячную квоту можно было бы сбросить, попросив продавца
перезагрузить сервер.

Клиент, исчерпавший квоту или подписку, отключается и при следующей попытке
получает **сайт-прикрытие** — ровно то же, что видит посторонний. Отвечать
по-разному на «ключ не найден» и «квота кончилась» нельзя: эта разница видна
снаружи и превращается в способ прощупать ноду.

Ключ клиента задаётся флагом `-key` или переменной `VEIL_CLIENT_KEY`. Без него
клиент генерирует временный при каждом запуске — удобно для отладки, но нода
тогда не отличает одного клиента от другого.

## Панель

Управляющий слой: подписчики, ключи, ноды, статистика. Пользовательский трафик
через панель не идёт никогда — её домен светится только в момент обновления
подписки.

```bash
./bin/veil-panel -new-token                  # выпустить админский токен
VEIL_ADMIN_TOKEN=<токен> ./bin/veil-panel -db veil.db -sub-base https://sub.example.com
```

Панель отдаёт голый HTTP и **обязана стоять за обратным прокси с TLS**: по её
API ходят токены, а в ответах уезжают приватные ключи подписчиков.

### Веб-интерфейс

Открой корень панели в браузере и введи админский токен — он останется в этом
браузере. Страница вшита в бинарник: копировать на сервер по-прежнему нужно
один файл.

Что там есть:

- **Выдать доступ** — метка, срок, квота, лимит устройств и галочки видов
  доступа. После создания сразу открывается окно со всеми ссылками и кнопками
  «Копировать»: ссылка для нашего клиента, адрес подписки и прямые ссылки на
  каждую ноду. Это и есть повседневная работа продавца — выдал, скопировал,
  отправил.
- **Список подписчиков** — расход с полосой заполнения квоты, срок в днях,
  какие виды доступа выданы. Кнопки: ссылки, продлить на 30 дней, отключить,
  выпустить ещё один доступ, удалить.
- **Ноды** — адрес, SNI, когда последний раз выходила на связь. При добавлении
  показывается готовая команда запуска с токеном ноды.

Страница отдаётся с жёсткой политикой безопасности: разрешён ровно один
скрипт, наш, опознаваемый по одноразовому значению, внешние адреса запрещены
вовсе. Причина простая: на этой странице лежит админский токен, и любой чужой
скрипт в этом origin означал бы полный доступ к панели. По той же причине все
данные ставятся в разметку как текст — метка подписчика вида
`<img src=x onerror=...>` отрисуется буквами, а не выполнится.

### API для телеграм-бота

Всё под токеном в заголовке `Authorization: Bearer <токен>`.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/v1/users` | завести подписчика, вернуть ключ и ссылку |
| `GET` | `/api/v1/users` | список с расходом |
| `PATCH` | `/api/v1/users/{id}` | продлить, отключить, поменять лимиты |
| `DELETE` | `/api/v1/users/{id}` | удалить |
| `POST` | `/api/v1/users/{id}/credentials` | выдать доступ ещё на одно устройство или для другого протокола |
| `DELETE` | `/api/v1/credentials/{id}` | отозвать одно устройство |
| `POST` | `/api/v1/nodes` | зарегистрировать ноду, вернуть её токен |
| `GET` | `/api/v1/nodes` | список нод: связь, доступность у клиентов, задержка |
| `POST` | `/sub/{token}/report` | отчёт клиента о доступности нод (токеном подписки) |
| `GET` | `/api/v1/users/{id}/links` | собрать ссылки заново для уже заведённого подписчика |

Продать месяц одним запросом:

```bash
curl -X POST https://panel.example.com/api/v1/users \
  -H "Authorization: Bearer $VEIL_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"label":"заказ 1043","traffic_limit":107374182400,"max_ips":3,"kinds":["vp1","vless","trojan"]}'
```

`kinds` — какие виды доступа выдать. Пусто означает только `vp1`. Продавцу,
переводящему покупателей с чужой панели, обычно нужны все три.

В ответе `issued` с секретами и `links` с готовыми ссылками:

```json
{
  "links": {
    "account": "veil-account://...",
    "subscription": "https://sub.example.com/sub/<токен>",
    "stock": [
      "vless://<uuid>@msk.example.com:443?encryption=none&fp=chrome&security=tls&sni=msk.example.com&type=tcp#msk",
      "trojan://<пароль>@msk.example.com:443?fp=chrome&security=tls&sni=msk.example.com&type=tcp#msk"
    ]
  }
}
```

`account` — для нашего клиента, `stock` — для приложений, которые у покупателя
уже стоят. Бот не должен склеивать ссылки сам: одна ошибка в параметрах — и
покупатель приходит с «не работает», а продавец не понимает, в чём дело.

**Секреты отдаются ровно один раз.** Для `vp1` панель приватную часть вообще
не хранит: утечка базы не даёт доступа ни к одному клиенту. Для `vless` и
`trojan` так не выйдет — там секрет это строка, которую обязаны знать обе
стороны, и панель хранит её в открытом виде, потому что ноде её надо отдать.
**Значит база панели с записями чужих протоколов — настоящий секрет, и её
утечка равносильна выдаче доступа всем таким клиентам.** Это и есть цена
совместимости.

### Ноды и панель

```bash
./bin/veil-server -panel https://panel.example.com -panel-token <токен ноды> ...
```

Нода раз в 15 секунд сдаёт расход и забирает свежий список. Если панель
недоступна — работает по последнему полученному списку: потерять панель на час
неприятно, отключить из-за этого всех клиентов недопустимо.

**Общая квота при нескольких нодах.** Каждая нода считает только свой трафик,
поэтому панель выдаёт ей лимит за вычетом израсходованного на других. Иначе
квоту в 100 ГБ можно было бы потратить на каждой ноде отдельно.

**Несколько устройств — один аккаунт.** У телефона и ноутбука разные ключи: их
видно по отдельности и любой отзывается отдельно. Но квота, срок и лимит
адресов у них общие, иначе достаточно попросить второй конфиг, чтобы удвоить
себе трафик.

### Подписка

`GET /sub/{token}` отдаёт ссылки на все ноды, свёрнутые в base64, — так, как
их ждут чужие приложения. В заголовке `Subscription-Userinfo` едет остаток
трафика и дата окончания: по нему приложения рисуют полоску квоты.

| Запрос | Что отдаёт | Кому |
|---|---|---|
| `/sub/{token}` | base64 со ссылками `vless://` и `trojan://` | v2rayNG, Hiddify, NekoBox |
| `/sub/{token}?format=raw` | то же, но без base64 | для отладки глазами |
| `/sub/{token}?format=json` | список нод со ссылками `veil://` и остатком квоты | наш клиент |

**Наши ссылки в обычную подписку не попадают намеренно.** Чужие клиенты не
знают схемы `veil://`, и часть из них спотыкается на незнакомой строке и не
принимает подписку целиком — то есть ломается именно у тех, ради кого всё
затевалось.

Секретов в подписке нет ни в одном из форматов: свой ключ покупатель получил
один раз в `account`, а список нод он обновляет постоянно и по открытому
каналу.

## Структура

```
cmd/veil-keygen     генерация ключей
cmd/veil-server     нода
cmd/veil-panel      панель: API, подписки, учёт
cmd/veil-client     клиент с локальным SOCKS5
internal/vp1        протокол: хендшейк, кадры, добивка, защита от повтора
internal/transport  транспорты: uTLS, TLS, REALITY, WebSocket за CDN
internal/inbound    чужие протоколы на нашей ноде: VLESS, Trojan, диспетчер
internal/fallback   настоящий сайт для тех, кто не прошёл аутентификацию
internal/rewind     отмотка прочитанного, чтобы гостя можно было отдать сайту
internal/mux        логические потоки внутри одного соединения (yamux)
internal/tunnel     пул сессий до ноды
internal/users      пользователи, квоты, учёт трафика, лимит устройств
internal/metered    счётчик байтов на соединении
internal/panel      хранилище и HTTP-интерфейс панели (SQLite)
internal/panel/web  страница панели, вшитая в бинарник
internal/nodesync   сторона ноды в разговоре с панелью
internal/socks5     минимальный SOCKS5-инбаунд
internal/relay      перекладывание байтов с корректным полузакрытием
docs/               архитектура и спецификация протокола
scripts/            локальная сквозная проверка
```

## Тесты

```bash
go test ./...
```

Три из них стоит знать по именам:

- `TestProbeSeesCoverSite` — зонд цензора получает настоящую страницу, а не
  признак прокси;
- `TestHalfCloseThroughStream` — сторона, закрывшая свою половину потока, всё
  ещё получает ответ (иначе страницы грузятся наполовину);
- `TestHandshakeSizesVary` — размеры хендшейка не постоянны, ловить их
  однострочным правилом нельзя;
- `TestUsageSurvivesRestart` — перезапуск ноды не обнуляет израсходованный
  трафик, квоту нельзя сбросить перезагрузкой сервера.
