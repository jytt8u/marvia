# Veil

Инфраструктура для обхода сетевой цензуры: собственный протокол, ядро, ноды,
управление и клиенты.

**Текущий этап: M3.** Работает шифрованный туннель с взаимной
аутентификацией, замаскированный под обычный HTTPS: клиент здоровается с
отпечатком Chrome, размеры пакетов размыты добивкой, десятки соединений
пользователя идут через одно соединение до ноды, а тот, кто пришёл без
правильного ключа, получает настоящий сайт вместо разрыва. Нода ведёт учёт
трафика по пользователям, следит за квотами, сроками подписки и числом
устройств.

- как всё устроено целиком — [docs/architecture.md](docs/architecture.md)
- протокол и то, что видно снаружи — [docs/protocol.md](docs/protocol.md)

## Сборка

Нужен Go 1.24+.

```bash
go build -o bin/ ./...
```

Четыре бинарника: `veil-keygen`, `veil-server`, `veil-client`, `veil-panel`.

Для Linux-ноды из-под Windows:

```bash
GOOS=linux GOARCH=amd64 go build -o bin/linux/ ./...
```

## Быстрый старт

**1. Ключи**

```bash
./bin/veil-keygen
```

Приватный остаётся на ноде, публичный нужен клиенту.

**2. Нода**

```bash
VEIL_SERVER_KEY=<приватный ключ> ./bin/veil-server -listen :443 -tls-cert fullchain.pem -tls-key privkey.pem -cover https://example.org
```

Ключ передавай переменной окружения или `-key-file`: значение флага `-key`
видно в `ps` любому пользователю машины.

`-cover` — адрес настоящего сайта, который увидит всякий, кто зайдёт на домен
ноды браузером или сканером. **Это не украшение, а защита**: нода, молча
рвущая непонятные соединения, вычисляется активным зондированием за пару дней.

### Маскировка REALITY

Вместо собственного сертификата нода может прикрываться чужим настоящим
сайтом. Тогда свой домен и сертификат не нужны вовсе.

```bash
./bin/veil-keygen -reality
```

```bash
VEIL_REALITY_KEY=<приватный ключ> ./bin/veil-server -listen :443 \
  -reality-dest www.samsung.com:443 -reality-sni www.samsung.com \
  -panel https://panel.example.com -panel-token <токен ноды>
```

Как это работает: на каждое входящее соединение нода открывает своё к сайту
прикрытия и зеркалит туда ClientHello. Тот, кто не доказал право входа,
получает **настоящий чужой сайт** — его содержимое и его подлинный
сертификат. Отличить ноду от зеркала того сайта нельзя, потому что в этот
момент она им и является.

Проверено вживую: `curl` с полной проверкой сертификата (`ssl_verify_result 0`)
подключился к ноде, прикрытой `www.example.com`, и получил страницу, побайтно
совпадающую с настоящей.

Чем это лучше обычного TLS с нашим сертификатом:

| | Свой сертификат | REALITY |
|---|---|---|
| Отпечаток ответа | стандартный Go, отличается от nginx | берётся у настоящего сайта |
| Свой домен | нужен, блокируется по SNI | не нужен вовсе |
| Что видит сканер | наш сайт-заглушку | чужой популярный сайт с валидным замком |
| Продление сертификата | нужно | не нужно |

**Как выбирать сайт прикрытия.** Он должен поддерживать TLS 1.3 и HTTP/2, быть
популярным, не принадлежать тебе и не лежать в подсети ноды. Плохой выбор
выдаёт ноду: сайт, к которому из этой страны никто не ходит, сам по себе
аномалия.

`-reality-short-id` — короткие идентификаторы клиентов через запятую,
шестнадцатеричные. Позволяют отзывать группы клиентов, не меняя ключ ноды.

Публичный ключ REALITY нода печатает при запуске — его нужно вписать в панель
как `pbk`, чтобы в ссылки уходило `security=reality`.

**Наш клиент тоже умеет REALITY.** Клиентская сторона написана вручную:
готовой библиотеки не существует, `github.com/xtls/reality` — только сервер,
а клиент живёт внутри Xray-core, тащить который в мобильное приложение
целиком неразумно.

```bash
./bin/veil-client -server <адрес ноды>:443 -sni www.samsung.com \
  -reality-pbk <публичный ключ REALITY> -reality-sid <идентификатор> -pubkey <ключ ноды>
```

Правильность проверяется единственным осмысленным способом — живым
разговором с эталонным сервером. Тест `TestRealityClientAcrossFingerprints`
гоняет клиента против того самого `xtls/reality`, который используют Xray и
sing-box, на восьми отпечатках браузеров сразу.

Он же поймал настоящую ошибку. Свежие отпечатки Chrome шлют два обмена
ключами: гибридный постквантовый и обычный X25519. Нода сначала ищет обычный
и только при его отсутствии берёт половину гибрида — клиент делал наоборот,
и на Chrome 131 и новее общий секрет расходился. Проявлялось это худшим
образом: нода не узнавала клиента и молча отправляла его на сайт прикрытия,
то есть «интернет не работает» без единой внятной ошибки.

### Работа за CDN: адрес ноды не существует

REALITY прячет трафик, но не адрес. Под ковровую блокировку диапазонов
хостингов — как 4 августа 2026 года — попадает и безупречно замаскированная
нода, потому что её никто не разглядывал.

Ответ на это один: **не показывать адрес вовсе**. Пользователь подключается к
адресам CDN, за которыми живут миллионы обычных сайтов; заблокировать такой
диапазон целиком означает уронить пол-интернета.

```bash
./bin/veil-server -listen :443 -ws-path /assets/app.js \
  -tls-cert fullchain.pem -tls-key privkey.pem -cover https://example.org
```

Домен направляешь на CDN, CDN — на ноду. В конфиге покупателя стоит домен, а
не адрес сервера.

```bash
./bin/veil-client -server <адрес CDN>:443 -ws-host <домен> -ws-path /assets/app.js -pubkey <ключ>
```

Проверено вживую: 11 запросов пользователя прошли через одно соединение до
ноды — мультиплексирование работает и внутри WebSocket.

**Путь стоит делать неочевидным.** Перебор популярных вроде `/ws` или `/vless`
по всем адресам хостера — дешёвый способ искать ноды. При этом сам по себе
путь туннеля ничем не выделяется: запрос без переговоров о WebSocket получает
ровно то же, что и любой другой путь.

| Путь | Что отдаёт нода |
|---|---|
| `/` | сайт-прикрытие, 200 |
| `/ws`, `/vless`, `/api` | сайт-прикрытие, 404 |
| путь туннеля обычным запросом | сайт-прикрытие, 404 |
| путь туннеля с переговорами | туннель |

**CDN видит расшифрованный трафик** — он же терминирует TLS. Здесь окупается
слоёная архитектура: внутри WebSocket работает VP1 со своим шифрованием, и CDN
достаётся поток, который он прочитать не может.

**REALITY и CDN несовместимы.** REALITY требует прямого TCP до ноды, а CDN
расшифровывает TLS у себя. Это два ответа на две разные угрозы:

| Режим | Что прячет | Чем платим |
|---|---|---|
| REALITY на чистом адресе | трафик неотличим от чужого сайта | адрес виден, попадает под ковровые блокировки |
| WebSocket за CDN | адреса для цензора не существует | камуфляж слабее, CDN видит зашифрованный нами поток |

Продавец выбирает под конкретную ноду; панель собирает ссылки под оба режима.

**3. Клиент**

```bash
./bin/veil-client -server <домен>:443 -sni <домен> -pubkey <публичный ключ>
```

**4. Проверка**

```bash
curl -x socks5h://127.0.0.1:1080 https://api.ipify.org
```

Должен вернуться IP ноды. Схема именно `socks5h`: `h` означает, что домен
резолвит нода, иначе DNS-запросы уйдут мимо туннеля и выдадут всё, что ты
открываешь.

Проверить прикрытие — должен открыться сайт из `-cover`:

```bash
curl https://<домен>/
```

### Локальная проверка целиком

На Windows из PowerShell:

```powershell
.\scripts\smoke.ps1
```

На Linux, macOS и в Git Bash:

```bash
bash scripts/smoke.sh
```

Поднимает ноду и клиента на localhost с самоподписанным сертификатом и
проверяет три вещи: трафик через туннель ходит, мультиплексирование работает,
посторонний видит сайт-прикрытие.

### Отладка вручную

```bash
./bin/veil-server -key <приватный> -tls-self-signed cover.local -cover https://example.com
./bin/veil-client -server 127.0.0.1:8443 -sni cover.local -insecure -pubkey <публичный>
```

Флаг `-plain` с обеих сторон отключает маскировку целиком — удобно, когда
отлаживаешь сам протокол и не хочешь мешать слои.

## Клиент для Android

Приложение лежит в `android/`. Собирается одной командой, ставится на телефон,
поднимает системный VPN.

```bash
scripts/android.sh
```

```powershell
.\scripts\android.ps1
```

Готовый пакет — `android/app/build/outputs/apk/debug/app-debug.apk`, 16 МБ,
`arm64-v8a` и `armeabi-v7a`.

Перед первой сборкой нужен `ANDROID_HOME` и однажды поставленный NDK:

| Что | Зачем | Размер |
|---|---|---|
| Android SDK: command-line tools, platform 36, build-tools 36 | сборка пакета | ~600 МБ |
| Android NDK 28 | `gomobile bind` без него не работает | ~2,2 ГБ |
| `gomobile` | превращает ядро на Go в библиотеку для Android | несколько МБ |

Отдельный плагин Kotlin подключать не нужно и нельзя: с девятой версии
сборщик Android умеет Kotlin сам и обрывает сборку, если увидит старый плагин.

### Что делает Kotlin, а что Go

Kotlin делает ровно две вещи, и обе платформенные: выпрашивает у системы
сетевой интерфейс и не даёт себя выгрузить из памяти. Выбор ноды,
рукопожатие, разбор пакетов, учёт — всё в Go, том же самом, что работает на
сервере и на настольной машине под SOCKS. Продублированная логика расходится,
и расходится она молча.

Даже проверка ссылки доступа на экране идёт через ядро,
`Mobile.checkAccountLink`. Правило, что считать правильной ссылкой, живёт в
одном месте — иначе приложение и сервер однажды разойдутся во мнениях, и
разбираться в этом будет человек, который просто хотел включить интернет.

### Ошибка говорит покупателю, что делать

Ядро формулирует точно: `dial tcp: lookup panel.example: no such host`. Для
разбора это незаменимо, для покупателя — пустой звук. Он заплатил за интернет
и хочет знать, на что нажать.

Поэтому ядро сообщает вместе с подробностями ещё и **вид неудачи** —
`account`, `panel`, `nodes` или `system`, — а фразу под него подбирает
приложение:

```
Не подключилось
Не получается получить список серверов. Проверь, есть ли интернет
dial tcp: lookup panel.example.invalid: no such host      ← мелким, копируется
```

Разделение именно такое, а не «пусть ядро сразу пишет по-человечески», по двум
причинам. Русский текст интерфейса расползся бы по ядру, а нужен будет ещё на
фарси и на китайском — это те же страны, ради которых всё затевалось. И точный
текст никуда не девается: покупатель снимет экран целиком и пришлёт продавцу,
а тому нужна как раз нижняя строка. Поэтому её можно выделить и скопировать.

Вид едет первой строкой сообщения об ошибке. Не от хорошей жизни: наружу
gomobile отдаёт обычное исключение, и приложить к нему что-то, кроме текста,
некуда. Зато вид проставляется там же, где случилась неудача, а не угадывается
потом разбором текста — переформулируешь сообщение, и угадывание сломается
молча.

`TestConnectNamesFailureKind` следит, что вид действительно доезжает. Проверка
выглядит мелкой, но держит важное: перестанет проставляться вид — покупатель
увидит невнятное вместо «ключ не подошёл», и узнаем мы об этом от него.

### Дескриптор интерфейса принадлежит ядру

`VpnService` выдаёт дескриптор, а закрывает его gvisor. Значит владелец должен
быть один, и это Go: Kotlin отдаёт дескриптор через `detachFd` и больше к нему
не прикасается, а ядро закрывает его и при неудачном запуске, и при остановке.

Иначе вышло бы двойное закрытие. На Linux это не безобидная ошибка на пустом
месте: номер уже освободился, его занял другой сокет, и вторым закрытием мы
рвём чужое соединение — в случайном месте и без единой строчки в журнале.

### IPv6 заворачивается в туннель, даже когда у ноды его нет

Соблазн велик: не объявлять маршрут `::/0` и не связываться. Но тогда весь
трафик IPv6 пойдёт мимо туннеля, то есть цензор увидит ровно ту часть, которую
мы прячем. Пусть лучше соединение не состоится внутри туннеля: приложения
после этого сами переходят на IPv4.

### Свой трафик в свой туннель не заворачиваем

`addDisallowedApplication` на собственный пакет. Без этого соединение до ноды
пошло бы через интерфейс, который сам же к этой ноде и ведёт.

### Запросы имён уходят в туннель по TCP

Ядро перехватывает любой UDP на порт 53 — неважно, какой адрес приложение себе
прописало. Запрос имени, ушедший мимо туннеля, выдаёт цензору весь список
посещённых сайтов, даже когда сам трафик он расшифровать не может.

Свой стек TCP мы при этом не пишем: Android даёт сырые IP-пакеты, а туннелю
нужны соединения. Берём проверенный gvisor через `tun2socks` — по той же
причине, по которой не писали свой TLS.

### Подпись приложения

```bash
cd android && ./gradlew assembleRelease
```

Готовый пакет — `android/app/build/outputs/apk/release/app-release.apk`, 14 МБ.

Ключ подписи лежит **вне репозитория**: путь берётся из `VEIL_RELEASE_KEYS`, по
умолчанию — `veil-keys/veil-release.properties` рядом с каталогом проекта. Файла
нет — сборка выйдет неподписанной и честно об этом скажет, а не подпишется
молча отладочным ключом.

**Подпись — это личность приложения на всю жизнь.** Телефон принимает
обновление только за той же подписью, что и установленная версия. Потеряешь
ключ — обновить приложение у покупателей будет нечем, придётся просить каждого
удалить старое и поставить новое. Утечёт — кто угодно выпустит «обновление» от
твоего имени, и телефоны его примут.

Включены схемы подписи v2 и v3. v3 нужна ради одного: она единственная
позволяет однажды сменить ключ, не теряя установленные приложения, — а ключ
живёт тридцать лет, и за это время всякое бывает. v1 не нужна, это подпись для
Android 6 и старше.

**Сжатие кода намеренно выключено.** Выигрыш почти нулевой: из четырнадцати
мегабайт пакета тринадцать — ядро на Go, скомпилированное в машинный код, до
которого R8 не дотягивается вовсе. А риск настоящий: классы моста вызываются
через JNI, статический анализ обращений к ним не видит и выбрасывает их как
ненужные. Правила в `proguard-rules.pro` это чинят, но ошибка в них проявляется
не на сборке, а падением уже у покупателя.

### Что проверено на живом телефоне

Samsung Galaxy A51, Android 13, arm64:

- приложение ставится и запускается, экран рисуется, отступы под вырез камеры
  и панель навигации считаются верно, клавиатура не закрывает кнопку;
- вызов в ядро работает: неверная ссылка отвергается, и на экран приходит
  текст ошибки, написанный в Go, — «ожидалась схема veil-account://»;
- система принимает нашу службу как VPN: показывает своё окно согласия и
  переключает на нас активный VPN;
- при неудаче служба честно останавливается и не остаётся висеть в памяти;
- фразы под виды неудач доходят до экрана. Испорченный ключ даёт «Ключ доступа
  не подошёл. Возьми новый у продавца», недостижимая панель — «Не получается
  получить список серверов. Проверь, есть ли интернет», и под каждой мелким
  стоит точный текст из ядра.

Первый же запуск нашёл ошибку, которую сборка показать не могла: **причина
обрыва пропадала с экрана.** `shutdown` записывал её, следом `stopSelf` звал
`onDestroy`, а тот останавливался ещё раз и объявлял обычное «отключено»
поверх причины. Человек видел, что не работает, и не видел почему — худший
вид ошибки именно в такой программе. Теперь остановка происходит один раз, и
причина доходит до экрана целиком — проверено на том же телефоне:

```
Не подключилось
список нод: запрос подписки: Get "https://panel.example.invalid/sub/proverka
?format=json": dial tcp: lookup panel.example.invalid: no such host
```

**Отладка по Wi-Fi для этого не годится.** Как только туннель поднимается,
трафик `adbd` уходит в него вместе со всем остальным, и связь с телефоном
рвётся на середине проверки. Проверять надо по проводу.

### Туннель с телефона до интернета

Проверено на живой ноде: сервер в Фуджейре, телефон в России, между ними
REALITY под `www.samsung.com`.

```
Instagram   200 за 1,98 с
YouTube     200 за 1,17 с
Discord     200 за 0,74 с
ipinfo.io   77.74.201.167, Fujairah, AE
```

Панель списала с подписчика 20 МБ — учёт считает то же, что реально прошло.
На телефоне поднялся `tun0` с обоими адресами, IPv4 и IPv6, значок VPN в
строке состояния, на экране «Подключено. Нода: ae-1».

Зонд цензора при этом видит настоящий сайт. С машины в России, откуда шла
проверка, параметры рукопожатия ноды и подлинного `www.samsung.com` совпали
полностью:

```
                      наша нода            настоящий сайт
протокол              TLSv1.3              TLSv1.3
шифр                  AES_256_GCM_SHA384   AES_256_GCM_SHA384
ключ сервера          2048 бит             2048 бит
ALPN                  h2                   h2
проверка сертификата  0 (ok)               0 (ok)
```

Через ноду `curl` получает `301` и подлинный сертификат DigiCert, выданный
Samsung SDS. Проверялось и на TLS 1.2, и на 1.1 — нода ведёт себя как сайт на
каждой версии, включая отказ там, где отказывает сайт.

**Про обрывы соединений человеку не сообщается.** Отличить «приложение само
закрыло соединение на полуслове» от «нода умерла посреди передачи» на уровне
моста невозможно: адаптер gvisor делает `errors.New(err.String())` и
выбрасывает тип, оставляя голый текст. Сообщение, которое не различает эти
случаи, хуже молчания — оно приписывает `endpoint is closed for send` к
совершенно здоровому туннелю каждый раз, когда человек листает ленту и
обрывает загрузку. Сигнал при этом не теряется: если нода умерла, следующее
соединение не откроется, а об этом сообщается.

**Порт 8444 — временный.** Нода стоит не на 443 только потому, что на том
сервере :443 занят посторонним сайтом. В бою так нельзя: корпоративные и
гостиничные сети режут исходящие на нестандартные порты, да и TLS на 8444 сам
по себе примета — настоящие сайты там не живут.

### Чего ещё нет

- клиента под Windows нет: на компьютере покупатель пока пользуется
  чужими приложениями по ссылке `vless://`, которую отдаёт та же панель;
- автоподключения при включении телефона и режима «всегда включён»;
- разделения по приложениям — какие пускать в туннель, какие мимо.

## Установка панели

Положи рядом со скриптом `veil-panel`, `veil-server` и `veil-keygen` и запусти:

```bash
./install-panel.sh --domain panel.example.com
```

Панель встанет, **сама получит сертификат Let's Encrypt** и напечатает
админский токен — один раз. Дальше добавление нод идёт готовыми командами, и
бинарники панель раздаёт им сама из своего каталога `dist`.

Если на том же сервере будет стоять нода, она займёт 443 — тогда панели нужен
другой порт: `--port 8443`. Адрес подписки понесёт порт вместе с собой, клиент
это умеет.

### Сертификат панель получает сама

Раньше она отдавала голый HTTP и требовала обратный прокси. Логика была
разумная: сертификатами занимается nginx, панель занимается своим делом. На
практике это значило, что продавец, поднявший панель на отдельной машине,
обязан ради одной подписки освоить ещё и nginx с расписанием обновления.

Теперь `-acme-domain` — и сертификат берётся при первом обращении и
продлевается сам. Обратный прокси никуда не делся и остаётся правильным
выбором там, где он уже стоит: `-tls-cert` и `-tls-key` работают как прежде.

Хранилище сертификатов обязано переживать перезапуск, и установщик кладёт его
в `/opt/veil/acme`. Без постоянного хранилища каждый рестарт заказывал бы новый
сертификат, а у Let's Encrypt на домен всего пять штук в неделю: после пятого
перезапуска панель осталась бы без сертификата на неделю — а вместе с ней все
покупатели без обновления списка нод.

**Владение доменом проверяется по 80-му порту.** Второй способ, через TLS на
443-м, здесь не работает: этот порт обычно занят нодой, а нода на незнакомого
гостя отвечает сайтом прикрытия — проверка ушла бы в Samsung и не вернулась.

### Что установщик проверяет до того, как что-то менять

Домен обязан вести на этот сервер — сверяется запись A с внешним адресом
машины. Проверка стоит первой: у Let's Encrypt ограничено число неудачных
попыток, и упереться в этот предел из-за неверной записи DNS — обидный способ
потерять час.

Порт 80 занят — отказ с объяснением, зачем он нужен. Порт панели занят —
отказ с предложением взять другой.

В конце установщик ждёт, пока панель действительно ответит по https, и при
неудаче печатает журнал.

### Секретов нет в командной строке

Админский токен уезжает в `EnvironmentFile` с правами 600. В строке запуска
его видел бы любой пользователь системы через `ps`. Панель, как и нода,
работает **не от root**: права нужны только чтобы занять порты ниже 1024.

## Установка ноды одной командой

Продавец просит у панели приглашение и получает готовую строку:

```bash
curl -X POST https://panel.example.com/api/v1/nodes/invite \
  -H "Authorization: Bearer $VEIL_ADMIN_TOKEN"
```

```json
{
  "command": "curl -fsSL https://panel.example.com/install/<приглашение> | sh",
  "invite": { "expires_at": "…" }
}
```

Строку он вставляет на чистом сервере. Всё: ключи выпущены, нода записана в
панель, служба поднята и проверена. Ни одного флага, ни одного файла для
редактирования.

Поменять что-то можно переменными, не трогая скрипт:

```bash
curl -fsSL https://panel.example.com/install/<приглашение> | PORT=8443 DEST=www.icloud.com:443 NAME=amsterdam-1 sh
```

### Приглашение вместо админского токена

Установщику нужен доступ к панели, чтобы записать в неё новую ноду. Соблазн
был передать ему админский токен — и это была бы дыра во всё хозяйство: токен
осел бы на каждой ноде, а ноды стоят на дешёвых машинах в чужих странах и
живут под постоянным вниманием. Взлом одной такой машины отдал бы список
покупателей, их ключи и право выпускать новые доступы.

Поэтому — одноразовое приглашение. Оно даёт ровно одно право: **один раз
назваться нодой**. Живёт час, гасится в той же транзакции, в которой заводится
нода, и второй раз не срабатывает. Дальше нода работает своим токеном, которым
может только забирать свой список пользователей и сдавать расход.

`TestInviteOnlyWorksOnce` и `TestInviteGivesNoOtherRights` держат оба свойства.

### Установщик раздаёт сама панель

Скрипт и бинарники лежат по адресу `/install/<приглашение>`, а не на публичном
сайте. Причин две. Продавцу не нужно ничего нигде размещать — панель у него
уже есть. И посторонний, ткнувшийся в панель, ничего не найдёт: без живого
приглашения там обычный 404. Найденный установщик был бы однозначной вывеской
«здесь панель обхода блокировок».

Бинарники панель берёт из каталога `-dist`. Положить их туда — единственное
ручное действие при обновлении.

### Что установщик проверяет до того, как что-то менять

Порт занят — говорит об этом сразу, не скачав ни байта. Обнаружить занятость
после установки значит оставить человека с наполовину поставленной нодой.

Сайт прикрытия недоступен или не умеет TLS 1.3 — тоже отказ: с мёртвым
прикрытием нода не спрячется, а выяснилось бы это уже у покупателей.

Порт не 443 — предупреждение. Настоящие сайты на нестандартных портах не
живут, и это заметно со стороны; вдобавок корпоративные и гостиничные сети
такие порты режут.

В конце установщик ждёт, пока служба действительно поднимется, и при неудаче
печатает журнал. «Установка завершена» при упавшей службе — худшее, что он мог
бы сказать: человек уходит довольный, а работать начинает завтра.

### Адрес ноды определяет панель, а не нода

Нода не знает своего внешнего адреса: за NAT она видит внутренний, и в
конфигах покупателей оказалось бы `10.0.0.5`. Панель видит настоящий — тот, с
которого пришла регистрация, — и записывает его сама.

Если панель стоит за обратным прокси, адрес берётся из `X-Forwarded-For`, но
**только когда запрос пришёл из петли или частной сети**. Постороннему из
интернета заголовок не верим: иначе одного приглашения хватило бы, чтобы
записать ноду с чужим адресом — например с адресом сайта, который потом попал
бы в конфиги всех покупателей.

### Секретов нет в командной строке

Токен панели и приватный ключ REALITY уезжают в `EnvironmentFile` с правами
600, а ключ ноды лежит файлом и передаётся как `-key-file`. В строке запуска
их видел бы любой пользователь системы через `ps`.

Сама нода работает **не от root**: единственное, ради чего ей нужны были
права, — занять порт ниже 1024, и это выдаётся отдельной возможностью
`CAP_NET_BIND_SERVICE`.

## Отчёты о доступности и выбор ноды

Панель стоит за границей и видит ноду живой ровно тогда, когда для телефона в
Иркутске она уже мертва. Единственный, кто знает правду, — само устройство.

**Клиент меряет ноды сам** и подключается к самой быстрой живой. Меряется не
время установки TCP, а время до работающего туннеля: заблокированная нода
обычно принимает соединение и молча роняет пакеты уже во время TLS, так что
проверка «порт открыт» показала бы её живой.

**Результаты уходят панели** на `POST /sub/{token}/report` — тем же токеном
подписки. Админского токена на устройстве покупателя быть не должно ни при
каких обстоятельствах.

Панель складывает отчёты и ставит ноды в подписке в том порядке, в каком их
стоит пробовать. В интерфейсе у каждой ноды видно «сколько людей доходят» и
медианную задержку — продавец узнаёт о блокировке из панели, а не из
обращений в поддержку.

### Почему отчёты не отключают ноды

Отчёты приходят от клиентов, то есть из недоверенного источника. Если бы
жалоба была командой, любой покупатель выкинул бы все ноды продавца из
подписок и убил сервис без всякой блокировки.

Поэтому три правила:

| Правило | Что оно предотвращает |
|---|---|
| от каждого подписчика хранится один последний отчёт на ноду | накрутку количеством сообщений |
| ноды не отключаются, а только переставляются в списке | уничтожение сервиса одним вредителем |
| проблемной нода считается от трёх разных жалобщиков | ложные срабатывания от одного человека с плохой связью |

Худшее, чего добьётся вредитель, — подвинет живую ноду вниз списка.

## Пользователи, квоты и учёт

По умолчанию нода пускает любого, кто знает её публичный ключ. Для реальной
работы нужен файл пользователей — он же список того, кто и сколько может.

**Простой формат** — когда пользователей трое и лимиты не нужны:

```
# ноутбук
ЗДЕСЬ-ПУБЛИЧНЫЙ-КЛЮЧ-КЛИЕНТА-43-СИМВОЛА
```

**Полный формат** — с подписками и лимитами:

```json
{
  "users": [
    {
      "kind": "vp1",
      "secret": "ЗДЕСЬ-ПУБЛИЧНЫЙ-КЛЮЧ-КЛИЕНТА-43-СИМВОЛА",
      "label": "заказ 1043",
      "enabled": true,
      "expires_at": "2026-09-23T00:00:00Z",
      "traffic_limit": 107374182400,
      "max_ips": 3,
      "max_conns": 8,
      "account": "1043"
    },
    {
      "kind": "vless",
      "secret": "94183e3f-c094-4c62-9c8a-431fea85aa04",
      "label": "телефон",
      "enabled": true,
      "traffic_limit": 107374182400,
      "account": "1043"
    },
    {
      "kind": "trojan",
      "secret": "пароль",
      "label": "ноутбук",
      "enabled": true,
      "traffic_limit": 107374182400,
      "account": "1043"
    }
  ]
}
```

`kind` — вид доступа: `vp1` (умолчание, наш протокол), `vless` или `trojan`.
Последние два нужны, чтобы покупатель пользовался приложением, которое у него
уже стоит: v2rayNG, Hiddify, NekoBox. Нода понимает все три на одном порту и
различает их по первым байтам.

`account` связывает наборы в один аккаунт: квота, срок и лимит адресов у них
общие. Без него каждый набор получил бы свой лимит, и достаточно было бы
попросить второй конфиг, чтобы удвоить себе трафик.

Прежнее поле `public_key` по-прежнему понимается и означает то же, что
`secret` при `kind: vp1`.

```bash
./bin/veil-server -users users.json
```

| Поле | Что делает |
|---|---|
| `enabled` | `false` — доступ приостановлен, статистика сохраняется |
| `expires_at` | конец подписки; пусто — бессрочно |
| `traffic_limit` | байт всего; 0 — без лимита |
| `max_ips` | со скольких разных адресов можно подключаться в течение часа |
| `max_conns` | одновременных соединений до ноды; с мультиплексированием одно устройство открывает до четырёх |

`max_ips` — ответ на главную боль продавца: один купил, раздал конфиг
десятерым. Считать устройства напрямую нельзя, все предъявляют один ключ, а
вот разные адреса видно. Окно в час выбрано, чтобы переход с Wi-Fi на
мобильную сеть не упирался в лимит.

**Файл перечитывается на лету**, каждые 5 секунд по времени изменения:
панель или скрипт бота просто перезаписывают его. Если файл окажется битым,
нода продолжит работать по прошлому списку — отключить всех из-за опечатки
в конфиге хуже, чем на минуту отстать от изменений.

**Расход пишется рядом**, в `users.json.usage.json` (переопределяется флагом
`-usage`), каждые 30 секунд и при остановке. Перезапуск ноды не обнуляет
счётчики — иначе месячную квоту можно было бы сбросить, попросив продавца
перезагрузить сервер.

Клиент, исчерпавший квоту или подписку, отключается и при следующей попытке
получает **сайт-прикрытие** — ровно то же, что видит посторонний. Отвечать
по-разному на «ключ не найден» и «квота кончилась» нельзя: эта разница видна
снаружи и превращается в способ прощупать ноду.

Ключ клиента задаётся флагом `-key` или переменной `VEIL_CLIENT_KEY`. Без него
клиент генерирует временный при каждом запуске — удобно для отладки, но нода
тогда не отличает одного клиента от другого.

## Панель

Управляющий слой: подписчики, ключи, ноды, статистика. Пользовательский трафик
через панель не идёт никогда — её домен светится только в момент обновления
подписки.

```bash
./bin/veil-panel -new-token                  # выпустить админский токен
VEIL_ADMIN_TOKEN=<токен> ./bin/veil-panel -db veil.db -sub-base https://sub.example.com
```

Панель отдаёт голый HTTP и **обязана стоять за обратным прокси с TLS**: по её
API ходят токены, а в ответах уезжают приватные ключи подписчиков.

### Веб-интерфейс

Открой корень панели в браузере и введи админский токен — он останется в этом
браузере. Страница вшита в бинарник: копировать на сервер по-прежнему нужно
один файл.

Что там есть:

- **Выдать доступ** — метка, срок, квота, лимит устройств и галочки видов
  доступа. После создания сразу открывается окно со всеми ссылками и кнопками
  «Копировать»: ссылка для нашего клиента, адрес подписки и прямые ссылки на
  каждую ноду. Это и есть повседневная работа продавца — выдал, скопировал,
  отправил.
- **Список подписчиков** — расход с полосой заполнения квоты, срок в днях,
  какие виды доступа выданы. Кнопки: ссылки, продлить на 30 дней, отключить,
  выпустить ещё один доступ, удалить.
- **Ноды** — адрес, SNI, когда последний раз выходила на связь. При добавлении
  показывается готовая команда запуска с токеном ноды.

Страница отдаётся с жёсткой политикой безопасности: разрешён ровно один
скрипт, наш, опознаваемый по одноразовому значению, внешние адреса запрещены
вовсе. Причина простая: на этой странице лежит админский токен, и любой чужой
скрипт в этом origin означал бы полный доступ к панели. По той же причине все
данные ставятся в разметку как текст — метка подписчика вида
`<img src=x onerror=...>` отрисуется буквами, а не выполнится.

### API для телеграм-бота

Всё под токеном в заголовке `Authorization: Bearer <токен>`.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/v1/users` | завести подписчика, вернуть ключ и ссылку |
| `GET` | `/api/v1/users` | список с расходом |
| `PATCH` | `/api/v1/users/{id}` | продлить, отключить, поменять лимиты |
| `DELETE` | `/api/v1/users/{id}` | удалить |
| `POST` | `/api/v1/users/{id}/credentials` | выдать доступ ещё на одно устройство или для другого протокола |
| `DELETE` | `/api/v1/credentials/{id}` | отозвать одно устройство |
| `POST` | `/api/v1/nodes` | зарегистрировать ноду, вернуть её токен |
| `GET` | `/api/v1/nodes` | список нод: связь, доступность у клиентов, задержка |
| `POST` | `/sub/{token}/report` | отчёт клиента о доступности нод (токеном подписки) |
| `GET` | `/api/v1/users/{id}/links` | собрать ссылки заново для уже заведённого подписчика |

Продать месяц одним запросом:

```bash
curl -X POST https://panel.example.com/api/v1/users \
  -H "Authorization: Bearer $VEIL_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"label":"заказ 1043","traffic_limit":107374182400,"max_ips":3,"kinds":["vp1","vless","trojan"]}'
```

`kinds` — какие виды доступа выдать. Пусто означает только `vp1`. Продавцу,
переводящему покупателей с чужой панели, обычно нужны все три.

В ответе `issued` с секретами и `links` с готовыми ссылками:

```json
{
  "links": {
    "account": "veil-account://...",
    "subscription": "https://sub.example.com/sub/<токен>",
    "stock": [
      "vless://<uuid>@msk.example.com:443?encryption=none&fp=chrome&security=tls&sni=msk.example.com&type=tcp#msk",
      "trojan://<пароль>@msk.example.com:443?fp=chrome&security=tls&sni=msk.example.com&type=tcp#msk"
    ]
  }
}
```

`account` — для нашего клиента, `stock` — для приложений, которые у покупателя
уже стоят. Бот не должен склеивать ссылки сам: одна ошибка в параметрах — и
покупатель приходит с «не работает», а продавец не понимает, в чём дело.

**Секреты отдаются ровно один раз.** Для `vp1` панель приватную часть вообще
не хранит: утечка базы не даёт доступа ни к одному клиенту. Для `vless` и
`trojan` так не выйдет — там секрет это строка, которую обязаны знать обе
стороны, и панель хранит её в открытом виде, потому что ноде её надо отдать.
**Значит база панели с записями чужих протоколов — настоящий секрет, и её
утечка равносильна выдаче доступа всем таким клиентам.** Это и есть цена
совместимости.

### Ноды и панель

```bash
./bin/veil-server -panel https://panel.example.com -panel-token <токен ноды> ...
```

Нода раз в 15 секунд сдаёт расход и забирает свежий список. Если панель
недоступна — работает по последнему полученному списку: потерять панель на час
неприятно, отключить из-за этого всех клиентов недопустимо.

**Общая квота при нескольких нодах.** Каждая нода считает только свой трафик,
поэтому панель выдаёт ей лимит за вычетом израсходованного на других. Иначе
квоту в 100 ГБ можно было бы потратить на каждой ноде отдельно.

**Несколько устройств — один аккаунт.** У телефона и ноутбука разные ключи: их
видно по отдельности и любой отзывается отдельно. Но квота, срок и лимит
адресов у них общие, иначе достаточно попросить второй конфиг, чтобы удвоить
себе трафик.

### Подписка

`GET /sub/{token}` отдаёт ссылки на все ноды, свёрнутые в base64, — так, как
их ждут чужие приложения. В заголовке `Subscription-Userinfo` едет остаток
трафика и дата окончания: по нему приложения рисуют полоску квоты.

| Запрос | Что отдаёт | Кому |
|---|---|---|
| `/sub/{token}` | base64 со ссылками `vless://` и `trojan://` | v2rayNG, Hiddify, NekoBox |
| `/sub/{token}?format=raw` | то же, но без base64 | для отладки глазами |
| `/sub/{token}?format=json` | список нод со ссылками `veil://` и остатком квоты | наш клиент |

**Наши ссылки в обычную подписку не попадают намеренно.** Чужие клиенты не
знают схемы `veil://`, и часть из них спотыкается на незнакомой строке и не
принимает подписку целиком — то есть ломается именно у тех, ради кого всё
затевалось.

Секретов в подписке нет ни в одном из форматов: свой ключ покупатель получил
один раз в `account`, а список нод он обновляет постоянно и по открытому
каналу.

## Структура

```
cmd/veil-keygen     генерация ключей
cmd/veil-server     нода
cmd/veil-panel      панель: API, подписки, учёт

internal/inbound    чужие протоколы на нашей ноде: VLESS, Trojan, диспетчер
internal/fallback   настоящий сайт для тех, кто не прошёл аутентификацию
internal/rewind     отмотка прочитанного, чтобы гостя можно было отдать сайту
internal/mux        логические потоки внутри одного соединения (yamux)

internal/users      пользователи, квоты, учёт трафика, лимит устройств

internal/panel/web  страница панели, вшитая в бинарник
internal/nodesync   сторона ноды в разговоре с панелью
internal/socks5     минимальный SOCKS5-инбаунд
internal/relay      перекладывание байтов с корректным полузакрытием

```

## Тесты

```bash
go test ./...
```

Три из них стоит знать по именам:

- `TestProbeSeesCoverSite` — зонд цензора получает настоящую страницу, а не
  признак прокси;
- `TestHalfCloseThroughStream` — сторона, закрывшая свою половину потока, всё
  ещё получает ответ (иначе страницы грузятся наполовину);
- `TestHandshakeSizesVary` — размеры хендшейка не постоянны, ловить их
  однострочным правилом нельзя;
- `TestUsageSurvivesRestart` — перезапуск ноды не обнуляет израсходованный
  трафик, квоту нельзя сбросить перезагрузкой сервера.
