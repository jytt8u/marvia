# API для телеграм-бота

Бота пишет продавец: у каждого своя оплата, свой язык общения с покупателем,
свои тарифы. Наше дело — чтобы на этом пути не было граблей.

## Ключ для бота

Боту нужен **свой ключ**, а не админский токен. Админским продавец входит в
панель; отдать его боту — значит дать право удалить всех покупателей и увести
базу с секретами vless и trojan, а при утечке отозвать его нельзя, не выкинув
из панели себя самого.

Выпускается один раз, админским токеном:

```bash
curl -X POST https://panel.example.com/api/v1/keys \
  -H "Authorization: Bearer $VEIL_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name": "телеграм-бот", "scopes": ["users"]}'
```

В ответе `secret` вида `vk_…` — он показывается **один раз**, в базе остаётся
только хеш. Дальше все запросы бота идут с ним:

```
Authorization: Bearer vk_…
```

Права:

| Право | Что даёт |
|---|---|
| `users` | завести покупателя, продлить, отключить, удалить, выдать ссылки |
| `nodes` | добавить ноду, удалить, пригласить новый сервер |
| `read` | только смотреть; входит в любое другое право |

**Боту хватает `users`.** Он не добавляет серверы — это делает человек.

Посмотреть выпущенные (`GET /api/v1/keys`) и отозвать (`DELETE /api/v1/keys/{id}`)
можно только админским токеном: ключ, умеющий выпускать ключи, ничем не
отличается от админского. В списке видно, когда каждым пользовались последний
раз — по этому и понятно, какой ещё живой.

Отзыв действует сразу, следующий же запрос получает `401`.

Админский токен по-прежнему работает везде: у продавца, который уже написал
бота на нём, ничего не сломается от обновления панели. Но переехать стоит.

## Продажа

```bash
curl -X POST https://panel.example.com/api/v1/users \
  -H "Authorization: Bearer $VEIL_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
        "external_id":   "tg:584930221",
        "label":         "заказ 1043",
        "expires_at":    "30d",
        "traffic_limit": 107374182400,
        "max_ips":       3,
        "kinds":         ["vp1", "vless", "trojan"]
      }'
```

В ответе — готовые ссылки:

```json
{
  "created": true,
  "user": { "id": 17, "external_id": "tg:584930221", "expires_at": "..." },
  "links": {
    "account":      "veil-account://…",
    "subscription": "https://panel.example.com/sub/…",
    "stock":        ["vless://…", "trojan://…"]
  }
}
```

`account` — для нашего приложения. `stock` — для тех, у кого уже стоит
v2rayNG, Hiddify или NekoBox. **Склеивать ссылки самому не надо:** одна ошибка
в параметрах — и покупатель приходит с «не работает», а разбираться будешь ты.

### external_id обязателен

Положи туда идентификатор покупателя в телеграме. Он делает две вещи.

**Позволяет найти покупателя, не держа вторую базу.** Иначе боту пришлось бы
самому помнить, какой telegram id какому номеру в панели соответствует, — а
при потере этой таблицы связь покупателей с подписками исчезнет.

**Защищает от двойной выдачи.** Платёжные системы повторяют уведомление, если
бот не ответил, а бот мог упасть ровно между вызовом панели и записью у себя.
Повторный запрос с тем же `external_id` **ничего не создаёт**: панель отвечает
успехом, возвращает существующего подписчика и ставит `"created": false`.
Новых секретов при этом не выдаёт.

То есть повтор безопасен по построению, и городить защиту в боте не нужно.

## Продление

```bash
curl -X PATCH https://panel.example.com/api/v1/users/17 \
  -H "Authorization: Bearer $VEIL_KEY" \
  -d '{"extend_by": "30d"}'
```

**Не считай новый срок сам.** `extend_by` прибавляет к тому, что осталось:
покупатель, продливший за неделю до конца, эту неделю не теряет. А если
подписка давно истекла — считается от сегодня, и вернувшийся через полгода не
покупает месяц, истёкший пять месяцев назад.

Ещё важнее: продление считается одной транзакцией. Бот, который читает срок,
прибавляет месяц и записывает обратно, теряет один платёж, когда два приходят
одновременно, — и узнаёт об этом от покупателя.

Назначить срок абсолютно можно через `expires_at`, но вместе с `extend_by` он
не работает: панель откажет, а не выберет одно из двух молча.

## Найти покупателя

```bash
curl "https://panel.example.com/api/v1/users?external_id=tg:584930221" \
  -H "Authorization: Bearer $VEIL_KEY"
```

Нет такого — `404`. Есть — список из одного.

Ответ несёт `used` (израсходовано байт), `traffic_limit`, `expires_at` и
`enabled`. Этого хватает и на «сколько у меня осталось», и на напоминание за
три дня до конца: пройди раз в сутки по `GET /api/v1/users` и отбери тех, у
кого срок близко.

## Отключить и включить

```bash
curl -X PATCH .../api/v1/users/17 -d '{"enabled": false}'
```

Отключение действует **сразу**, в том числе на тех, кто прямо сейчас качает:
ноды проверяют это каждые пять секунд и обрывают соединения.

## Второе устройство

```bash
curl -X POST .../api/v1/users/17/credentials -d '{"kind": "vless"}'
```

Квота, срок и лимит адресов у всех наборов доступа общие — иначе достаточно
попросить второй конфиг, чтобы удвоить себе трафик. А отзывается каждый
отдельно: потерял телефон — отзови только его.

## Что бот должен переслать покупателю

1. **Файл приложения** — `app-release.apk`.
2. **Ссылку `account`** — её человек вставляет в приложение.
3. **Одну ссылку из `stock`** — на случай, если он на компьютере.

Секреты отдаются **ровно один раз**, при выдаче. Панель приватную часть `vp1`
не хранит вовсе: утечка её базы не даёт доступа ни к одному покупателю нашего
протокола. Поэтому бот обязан переслать ссылки сразу — второй раз их взять
неоткуда, придётся выдавать новый доступ.

## Коды ответов

| Код | Что значит |
|---|---|
| `200` | получилось; смотри `created`, если это была продажа |
| `400` | панель не поняла запрос — текст в поле `error` |
| `401` | ключ не тот или отозван |
| `403` | ключу не хватает права — в ответе сказано, какого |
| `404` | нет такого покупателя |
| `500` | сломалась панель, повтори позже |

Тело ошибки всегда одинаковое: `{"error": "текст по-русски"}`.
